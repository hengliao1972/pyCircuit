\chapter{Vector Micro-Instructions}
\label{chap:vector-instructions}

\section{What This Chapter Is About}
This chapter documents the UOP Engine-generated vector micro-instruction surface: the 43 \texttt{u\_vec.*} opcodes that implement PTO tile instructions. These micro-instructions are never fetched as CPU-visible instructions. They are generated by the UOP Engine from stored templates or hardware generation logic and selected by the UOP Engine entry that the decoded \texttt{B.OP} bundle points to.

Think of this chapter as the \textit{implementer's reference} for the vector execution datapath. The tile instruction surface (\texttt{TADD}, \texttt{TROWSUM}, etc.) is the programmer-facing ISA; this chapter is the ISA of the vector ALU, the memory pipeline, and the mask pipeline beneath it.

The chapter is organized by functional family. Each family page explains the micro-instruction contract, operand slots, result types, masking rules, and the microcode-site budget. Individual micro-instruction entries give precise pseudocode.

\section{Why a Separate Micro-Instruction Layer?}
PTO tile instructions are complex enough that encoding their full semantics directly into a 32-bit or 64-bit CPU opcode would be impossible. Instead, each tile instruction selects a microcode body: a fixed sequence of \texttt{u\_vec.*} micro-instructions. The tile instruction encoding tells the decoder which UOP Engine entry to use; the microcode body tells the vector datapath what to do.

This separation is intentional. It means that:
\begin{itemize}
  \item A tile instruction's semantics can be arbitrarily complex (loops, nested conditionals, scatter-gather) without changing the CPU-visible encoding.
  \item The same tile instruction family (e.g. \texttt{TADD}) can have different microcode implementations for different element widths or layouts, selected by the \texttt{variant} field.
  \item Hardware can cache microcode bodies in a micro-instruction buffer and avoid the UOP Engine microcode generation on hot paths.
  \item The same \texttt{u\_vec.*} surface is shared by all tile instructions that need, say, a vector addition --- the \texttt{vadd} micro-instruction appears in \texttt{TADD}, \texttt{TADDS}, \texttt{TMUL}, and dozens of other microcode bodies.
\end{itemize}

The cost is an extra translation step. The programmer does not see \texttt{u\_vec.*}; the compiler backend does.

Each micro-instruction operates on typed operand slots. The slot types are encoded in the WM half:

\section{Masking and Lane Behaviour}
All vector micro-instructions execute under a per-lane mask. The mask is emitted by the tile metadata path and consumed by the micro-instruction. Lanes with mask=0 do not produce results and do not participate in arithmetic (except for predicated stores, which may write zeros or may not write at all depending on the store mode).

The mask is computed from the tile's valid region and any instruction-level predicate. For a tile with valid rows $R_v$ and valid columns $C_v$, the valid region covers lanes $(r, c)$ where $0 \le r < R_v$ and $0 \le c < C_v$. Lanes outside the valid region are masked off.

Some micro-instructions (e.g. \texttt{vbr} for broadcast, \texttt{vdup}) operate on a single source element replicated across lanes; these are typically masked with a scalar-width mask (mask=1 for the first lane, 0 for others) when used to initialize accumulators.

\section{Memory Micro-Instructions: \texttt{u\_vec.vlds} and \texttt{u\_vec.vsts}}
\index{vlds}\index{vsts}
Memory micro-instructions move data between tile storage and the vector staging registers. \texttt{vlds} loads a vector from tile storage into a staging register; \texttt{vsts} stores a staging register to tile storage.

These are the two highest-site-count micro-instructions in the catalog (130 and 97 static sites respectively) because they have the largest number of format-layout-variant combinations. A \texttt{vlds} for \texttt{f16} in row-major order is a different microcode site than \texttt{vlds} for \texttt{i32} in column-major order.

\subsection{Semantics}
\texttt{vlds} reads a tile-shaped region from tile storage (selected by the decoded source tile descriptor) into a staging register. The address within the tile is a function of the lane index, the row/column stride, and the element format. \texttt{vsts} performs the reverse: it writes the contents of a staging register to a tile storage location.

Both micro-instructions are gated by the active mask. For \texttt{vlds}, masked-off lanes produce undefined values in the staging register. For \texttt{vsts}, masked-off lanes do not write to tile storage.

The \texttt{plds} micro-instruction loads a predicate (a bitvector, one bit per lane) from tile storage into a mask register. It uses a compressed packing format (16 bits per lane in \texttt{pintlv\_b16}) and is used primarily in select and argmax/argmin operations.

\section{Arithmetic Micro-Instructions: \texttt{u\_vec.vadd}, \texttt{vsub}, \texttt{vmul}, \texttt{vdiv}}
\index{vadd}\index{vsub}\index{vmul}\index{vdiv}
Vector arithmetic micro-instructions perform lane-wise computation on staging register operands. All arithmetic respects IEEE 754 for floating-point operands; integer arithmetic is two's complement.

Each arithmetic micro-instruction is identified by its opcode and variant. The variant encodes rounding mode (for FP division and conversion), saturation mode (for integer operations), and lane-width behaviour.

\subsection{\texttt{vadd} --- Lane-wise addition}
Adds two staging register operands lane-by-lane. For integer types the result is $a + b$ modulo $2^{N}$. For FP types the result is $a + b$ with IEEE 754 rounding.

Common variants: \texttt{var=0} (round-to-nearest-even), \texttt{var=1} (round-toward-zero), \texttt{var=2} (round-toward-plus-infinity), \texttt{var=3} (round-toward-minus-infinity).

\subsection{\texttt{vsub} --- Lane-wise subtraction}
Subtracts slot B from slot A lane-by-lane: $a - b$.

\subsection{\texttt{vmul} --- Lane-wise multiplication}
Multiplies two operands lane-by-lane. FP multiplication follows IEEE 754. For integer multiplication, the result width is the same as the input width; overflow wraps modulo $2^{N}$. The signed (\texttt{si*}) element formats use saturating arithmetic instead of wrapping.

\subsection{\texttt{vdiv} --- Lane-wise division}
Divides slot A by slot B lane-by-lane: $a / b$. Division by zero produces an Inf (IEEE 754) with the dividend's sign. The variant field selects the rounding mode.

Note: integer division (\texttt{vdiv}) with \texttt{divu}-style unsigned operands requires the operand types to be correctly declared as \texttt{ui32} etc. in the microcode body; the micro-instruction itself does not distinguish signed from unsigned. The distinction is made at the tile instruction level by the \texttt{DataType} selector.

\section{Scalar-Broadcast Arithmetic: \texttt{u\_vec.vadds}, \texttt{vmuls}, \texttt{vshls}, \texttt{vshrs}}
\index{vadds}\index{vmuls}\index{vshls}\index{vshrs}
These micro-instructions are binary operations where one operand is a scalar imported from a GPR through \texttt{B.IOR} and the other is a vector staging register. The scalar is broadcast: every active lane uses the same scalar value.

Example: \texttt{vadds} computes $a_i + scalar$ for each lane $i$. This is the micro-instruction that \texttt{TADDS} (tile-plus-scalar) uses.

The microcode body for a scalar-broadcast tile instruction typically:
\begin{enumerate}
  \item Emits \texttt{vbr} to broadcast the imported scalar into a staging register.
  \item Executes the binary arithmetic micro-instruction against the vector operand.
\end{enumerate}

\section{Logical and Bitwise: \texttt{u\_vec.vand}, \texttt{vor}, \texttt{vxor}, \texttt{vnot}}
\index{vand}\index{vor}\index{vxor}\index{vnot}
These are lane-wise bitwise operations on integer vector operands. For FP types, the operation is applied to the bit representation (i.e. they behave as if the FP value is an unsigned integer of the same width). This is useful for sign manipulation, absolute value (\texttt{vand(x, mask)} with mask = sign\_bit\_clear), and bit-field extraction.

\section{Unary Transforms: \texttt{u\_vec.vneg}, \texttt{vabs}, \texttt{vrelu}, \texttt{vlrelu}}
\index{vneg}\index{vabs}\index{vrelu}\index{vlrelu}
Unary micro-instructions read one staging register and produce one result. All are masked.

\texttt{vneg} computes the two's-complement negation: $-a$. For unsigned integer types the behaviour is defined modulo $2^{N}$. For FP types, \texttt{vneg} flips the sign bit.

\texttt{vabs} computes the absolute value. For FP types this is $a \text{ with sign bit cleared}$. For signed integer types, the behaviour depends on the element format: \texttt{i8/i16/i32} wraps (the negation of INT\_MIN is INT\_MIN); \texttt{si8/si16/si32} saturates (INT\_MIN becomes INT\_MAX).

\texttt{vrelu} computes $\max(0, a)$ lane-by-lane. \texttt{vlrelu} computes the leaky ReLU: $\max(0, a) + \alpha \cdot \min(0, a)$ where $\alpha$ is a small constant defined by the element format variant.

These unary micro-instructions are the implementation primitives for \texttt{TNEG}, \texttt{TABS}, \texttt{TRELU}, and \texttt{TLRELU}.

\section{Comparison and Mask Generation: \texttt{u\_vec.vcmp}}
\index{vcmp}
\texttt{vcmp} compares two staging register operands and produces a mask (predicate bitvector) result. The comparison is ordered (NaN propagates; unordered comparisons are not provided at the micro-instruction level). The variant field selects the comparison predicate:

\begin{longtable}{@{}L{0.18\linewidth}L{0.30\linewidth}L{0.42\linewidth}@{}}
\toprule
Variant & Predicate name & Condition \\
\midrule
0 & eq & $a == b$ \\
1 & ne & $a \neq b$ \\
2 & lt & $a < b$ (signed) \\
3 & le & $a \le b$ (signed) \\
4 & lt (unsigned) & $a < b$ (unsigned interpretation) \\
5 & le (unsigned) & $a \le b$ (unsigned interpretation) \\
\bottomrule
\end{longtable}

The mask result is used by \texttt{vsel} to select between two sources, by \texttt{pbitcast} to convert between mask formats, and by branch micro-instructions (\texttt{vbr}) for within-body control flow.

\section{Selection and Conditional Move: \texttt{u\_vec.vsel}}
\index{vsel}
\texttt{vsel} is a ternary micro-instruction: \texttt{vsel(result, a, b, mask)} writes $a$ to \texttt{result} for lanes where \texttt{mask}=1 and $b$ for lanes where \texttt{mask}=0. This implements the \texttt{TSEL} and \texttt{TSELS} tile instructions and is also used inside argmax/argmin bodies to keep the best value and its index.

The mask operand is a \texttt{mask\_reg} slot type, not a boolean value. A \texttt{vcmp} followed by \texttt{vsel} is the standard idiom for predicated selection.

\section{Broadcast and Duplication: \texttt{u\_vec.vbr}, \texttt{vdup}}
\index{vbr}\index{vdup}
\texttt{vbr} (vector broadcast) broadcasts a scalar or narrow-vector value into a full-width staging register. It is used to initialize accumulators, broadcast scalar GPR imports across lanes, and construct constant vectors.

In microcode bodies, \texttt{vbr} typically appears with an immediate mask (mask=1 for the first lane only) to emit a scalar into a single lane, which is then either used directly or combined with other operations.

\texttt{vdup} (vector duplicate) replicates a single source element across all lanes of a staging register. Unlike \texttt{vbr} which reads from a staging register, \texttt{vdup} reads from the decoded immediate or a special narrow-vector source.

Both are masked: masked-off lanes produce undefined results in the destination.

\section{Format Conversion and Interleave: \texttt{u\_vec.vcvt}, \texttt{vbitcast}, \texttt{vintlv}, \texttt{vdintlv}}
\index{vcvt}\index{vbitcast}\index{vintlv}\index{vdintlv}
These micro-instructions manipulate the representation of vector data without changing the logical values (or, for \texttt{vcvt}, with changing them according to the conversion rules).

\texttt{vcvt} converts between element formats: FP to FP (different precision), FP to integer, integer to FP, or integer to integer with saturation. The variant field controls rounding mode. Converting from FP to integer with a value that is too large or NaN is defined by the target profile; it is typically a saturating conversion.

\texttt{vbitcast} reinterprets the bit pattern of a vector from one type to another without changing the bits. For example, casting \texttt{f32} to \texttt{i32} reads the IEEE 754 bit pattern as an integer. This is used in argmax/argmin to reinterpret the index from FP to integer format.

\texttt{vintlv} interleaves two half-width vectors into a full-width vector. It is the inverse of the \texttt{pintlv\_b16} predicate interleave. For example, given \texttt{[a0, a1, a2, a3]} and \texttt{[b0, b1, b2, b3]}, \texttt{vintlv} produces \texttt{[a0, b0, a1, b1, a2, b2, a3, b3]}.

\texttt{vdintlv} de-interleaves a full-width vector into two half-width vectors (the inverse of \texttt{vintlv}).

\section{Indexed Reduction: \texttt{u\_vec.vcmax}, \texttt{vcmin}}
\index{vcmax}\index{vcmin}
These micro-instructions perform an indexed max or min reduction over a staging register operand. The result is a pair: the extreme value and the lane index at which it occurred. Both are written to staging registers.

\texttt{vcmax} computes $\max_i a_i$ and returns $(a_{max}, \text{index}_{max})$. \texttt{vcmin} does the same for the minimum. These are the building blocks for \texttt{TROWARGMAX} and \texttt{TROWARGMIN}, which need both the extreme value and its column position.

The indexed form is necessary because a plain \texttt{vmax} micro-instruction would lose the lane information needed to recover the index.

\section{Complex-Data Arithmetic: \texttt{u\_vec.vcadd}}
\index{vcadd}
\texttt{vcadd} performs complex-data multiply-accumulate: given two complex vectors $a$ and $b$, it computes $a + b_{\text{conj}}$ element-wise. The conjugate is applied to slot B; the accumulator is slot A. This micro-instruction supports FFT and signal-processing tile operations.

\section{Predicate Micro-Instructions: \texttt{u\_vec.pbitcast}, \texttt{pintlv\_b16}, \texttt{pset\_b16}, \texttt{punpack}}
\index{pbitcast}\index{pintlv_b16}\index{pset_b16}\index{punpack}
Predicate micro-instructions manipulate the per-lane mask bitvector. The predicate format is compressed: 16 lanes are packed into one 16-bit word (\texttt{pintlv\_b16}). Operations on predicates must unpack, operate, and repack.

\texttt{pbitcast} converts a mask from one lane-width interpretation to another. For example, a 32-bit mask (one bit per f32 lane) can be cast to an 8-bit mask (one bit per i8 lane) by discarding the upper bits.

\texttt{pintlv\_b16} interleaves two 16-bit predicate words into a 32-bit predicate word. \texttt{pset\_b16} sets bits in a 16-bit predicate word based on a mask register. \texttt{punpack} unpacks a 16-bit predicate word into an implicit full-lane mask format.

These micro-instructions are used almost exclusively in argmax/argmin and select microcode bodies.

\section{Special Functions: \texttt{u\_vec.vexp}, \texttt{vln}, \texttt{vsqrt}}
\index{vexp}\index{vln}\index{vsqrt}
These micro-instructions invoke hardware accelerators for transcendental functions. They are single-site micro-instructions (each appears only once in the opcode map) because they are microcode-site-heavy --- the polynomial or CORDIC approximation takes many cycles and dedicated hardware.

\begin{longtable}{@{}L{0.20\linewidth}L{0.30\linewidth}L{0.40\linewidth}@{}}
\toprule
Micro-instruction & Function & Tile instruction that uses it \\
\midrule
\texttt{vexp} & $e^a$ (base-e exponential) & \texttt{TEXP} \\
\texttt{vln} & $\ln(a)$ (natural logarithm) & \texttt{TLOG} \\
\texttt{vsqrt} & $\sqrt{a}$ & \texttt{TSQRT}, \texttt{TRSQRT} \\
\bottomrule
\end{longtable}

Special-function micro-instructions follow IEEE 754 for defined inputs. The behaviour for negative inputs to \texttt{vln} and for negative or zero inputs to \texttt{vsqrt} is implementation-defined. Implementations should produce NaN.

\section{Memory Ordering: \texttt{u\_vec.mem\_bar}}
\index{mem_bar}
\texttt{mem\_bar} is a control micro-instruction that establishes an ordering boundary for tile memory side effects within a microcode body. It is used when a tile instruction body contains both a load and a store and the ordering between them must be preserved regardless of optimizations.

In the current microcode bodies, \texttt{mem\_bar} appears only in tile instruction forms that mix a load from one tile and a store to another within the same microcode body, to ensure that a speculative store does not become visible before the load that it depends on.
